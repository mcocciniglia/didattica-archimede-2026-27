Il server iterativo alla prova: due client, una sola volta

Coda delle connessioni, accept() e limite del modello iterativo.

Durata: 1 ora Strumenti: Python, Telnet e tre terminali Prerequisito: Lezione 2 Rete: solo questo computer

Riprendiamo il server iterativo

Una preparazione, molte connessioni

Nella Lezione 2 abbiamo costruito un server che rimane attivo dopo la disconnessione di un client. Oggi non cambiamo il programma: lo mettiamo alla prova con due client collegati nello stesso momento.

   ↓

    accept()
       ↓

       ↓

listen(): una volta

Prepara il socket server all’ascolto prima che inizi il ciclo dei client.

accept(): per ogni client

Restituisce al programma una nuova connessione da usare per dialogare con quel client.

Dopo listen(), il socket server rimane in ascolto anche mentre una singola connessione viene aperta e poi chiusa. Non occorre quindi prepararlo di nuovo: occorre invece ripetere accept() per ottenere la connessione di ciascun nuovo client.

Osserviamo il server

Che cosa sta succedendo?

CLIENT A ─────────► SERVER
                   SERVITO
                     │
                     ├─ recv()
                     ├─ sendall()
                     └─ recv()

CLIENT B ─────────► IN ATTESA

Il programma server sta ancora eseguendo il ciclo interno relativo al Client A. Finché quel ciclo non termina, il programma non può tornare alla successiva chiamata di accept().

Connessione TCP stabilita

Il sistema operativo può avere già completato la connessione TCP.

Connessione accettata e servita

Il programma ha ottenuto la connessione con accept() e sta eseguendo recv() e sendall() per quel client.

Connessione in attesa dell’applicazione

La connessione TCP può essere stabilita, ma il programma non l’ha ancora prelevata con una nuova accept(); quindi il client non riceve ancora la risposta applicativa.

Parola nuova

Coda delle connessioni

È l’area gestita dal sistema operativo in cui possono attendere le connessioni che il programma server non ha ancora prelevato con accept(). La sua capacità è limitata.

!
Connessione TCP e accept() non sono la stessa cosa.

Il sistema operativo gestisce la connessione di rete; accept() è invece la chiamata con cui il nostro programma ottiene una connessione pronta e può iniziare a servirla.

Breve richiamo

La connessione può precedere accept()

Breve richiamo: nel Transmission Control Protocol (TCP), il collegamento viene stabilito con il three-way handshake, cioè uno scambio in tre passaggi:

Client                Server

SYN ------------------>
    <--------------- SYN + ACK
ACK ------------------>

Lo scambio è gestito dal sistema operativo: una connessione può risultare stabilita mentre il programma server non ha ancora eseguito una nuova accept().

Per questo esperimento basta comprendere la distinzione tra connessione TCP stabilita e connessione già accettata dall’applicazione.

Il limite del modello

Molti nel tempo, uno alla volta

?

Un vero server web potrebbe servire migliaia di utenti aspettando che ciascuno termini prima di passare al successivo?

Client A ───────► ███████████
Client B ───────────────────► ███████
Client C ────────────────────────────► ██████

Ogni barra rappresenta il tempo durante il quale un client viene servito. B deve aspettare la fine di A; C deve aspettare sia A sia B. Se un client è lento o rimane collegato a lungo, ritarda tutti quelli che seguono.

Il server iterativo può gestire molti client nel tempo, ma ne serve uno alla volta. Questo è il suo principale limite.

!

Domanda-problema

Come possiamo continuare ad accettare nuovi client mentre ne stiamo già servendo uno?

SERVER
  │
  ├── Client A ──► ?
  ├── Client B ──► ?
  └── Client C ──► ?

Questa domanda introduce la successiva evoluzione del progetto: il server concorrente. Per ora non lo implementiamo.
