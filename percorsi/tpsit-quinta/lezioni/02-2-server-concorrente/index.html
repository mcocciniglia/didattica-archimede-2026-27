Lezione 2.2 · M2 · TPSIT · Classe quinta

Due client, davvero insieme: il server concorrente

Dal server iterativo a un thread per ogni client.

Durata: 1 ora Strumenti: Python e Telnet 3 terminali · localhost Prerequisito: 2.1

Ripartiamo dalla 2.1

B era collegato, ma doveva aspettare A

Nella Lezione 2.1 abbiamo lasciato aperto il Client A e collegato anche il Client B. La connessione di B poteva essere già nella coda, ma il programma server continuava a servire A.

  1. A rimane collegato.

    Il server resta nel ciclo di recv() e sendall() dedicato ad A.

  2. B si collega e attende.

    Il programma non è ancora tornato a una nuova accept().

  3. A chiude la connessione.

    Soltanto allora il ciclo interno termina.

  4. Il server torna ad accept().

    B viene finalmente accettato e servito.

?

Domanda guida

Come può il server tornare subito ad accept() senza aspettare che A abbia terminato?

Al termine

Che cosa saprai spiegare e verificare

Due lavori separati

Distinguere il thread principale, che accetta le connessioni, dal thread che comunica con un client.

Due tipi di socket

Distinguere l’unico socket server dai diversi socket conn restituiti da accept().

Due client serviti

Verificare che B riceva risposte mentre A è ancora collegato.

L’idea

Separare i due lavori

Il server deve continuare ad accettare nuove connessioni e, nello stesso intervallo di tempo, comunicare con i client già connessi. Affidiamo questi compiti a percorsi di esecuzione distinti:

✓

Il thread principale accetta le connessioni; un nuovo thread si occupa di ciascun client.

Parole nuove

Thread

È un percorso di esecuzione all’interno del programma. Qui ne creiamo uno con un solo compito: gestire il dialogo con uno specifico client.

Concorrenza

È l’organizzazione che permette a più attività di avanzare nello stesso intervallo di tempo. Non significa che ogni istruzione venga eseguita nello stesso preciso istante.

Non confondere i ruoli

Un socket ascolta, gli altri comunicano

Socket server

È uno solo. Viene preparato con bind() e listen(1); il thread principale lo usa per eseguire più volte accept().

Socket conn

È il socket della comunicazione con un client. Ogni accept() riuscita restituisce un nuovo conn e il relativo addr.

!

Attenzione a listen(1)

Il parametro di listen(1) riguarda la coda delle connessioni in attesa di essere accettate. Non limita a uno il numero di client già accettati e gestiti dai thread.

!

Non creiamo un nuovo server per ogni client.

listen() viene eseguito una sola volta e non viene chiamato nei thread dei client. Il thread principale continua invece a ripetere accept().

Prima modifica

Separiamo la gestione del client

Spostiamo il lavoro che prima si trovava direttamente nel ciclo principale dentro una funzione. Il comportamento del dialogo non cambia:

def gestisci_client(conn, addr):
    print("Client connesso:", addr)

    with conn:
        while True:
            dati = conn.recv(1024)

            if not dati:
                break

            messaggio = dati.decode().strip()
            print("Ricevuto da", addr, ":", messaggio)

            risposta = "Hai scritto: " + messaggio
            conn.sendall((risposta + "\n").encode())

    print("Client disconnesso:", addr)

La funzione riceve il socket conn e l’indirizzo addr di un solo client. Poi ripete le stesse operazioni già conosciute: riceve, costruisce la risposta e la invia.

Seconda modifica

Creiamo e avviamo un thread

All’inizio del programma importiamo il modulo necessario:

import threading

Dopo ogni accept() prepariamo un thread e lo avviamo:

thread = threading.Thread(
    target=gestisci_client,
    args=(conn, addr)
)

thread.start()

target

Indica la funzione che il nuovo thread dovrà eseguire.

args

Contiene i dati da passare alla funzione: il socket conn e l’indirizzo addr.

start()

Avvia il nuovo thread. Il thread principale può quindi proseguire e tornare rapidamente ad accept().

!

start() non è una chiamata diretta alla funzione.

Se scrivessimo gestisci_client(conn, addr), il thread principale eseguirebbe tutta la funzione e aspetterebbe la fine del client. Torneremmo così al comportamento sequenziale del server iterativo.

Il programma completo

Il server concorrente

Il dialogo con il client è stato spostato in gestisci_client(). Sono state aggiunte l’importazione di threading, la creazione del thread e la chiamata a start().

Scarica server.py
import socket
import threading


HOST = "127.0.0.1"
PORT = 50000


def gestisci_client(conn, addr):
    print("Client connesso:", addr)

    with conn:
        while True:
            dati = conn.recv(1024)

            if not dati:
                break

            messaggio = dati.decode().strip()
            print("Ricevuto da", addr, ":", messaggio)

            risposta = "Hai scritto: " + messaggio
            conn.sendall((risposta + "\n").encode())

    print("Client disconnesso:", addr)


def main():
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as server:
        server.bind((HOST, PORT))
        server.listen(1)

        print(f"Server in ascolto su {HOST}:{PORT}")

        while True:
            conn, addr = server.accept()

            thread = threading.Thread(
                target=gestisci_client,
                args=(conn, addr)
            )

            thread.start()


if __name__ == "__main__":
    main()

Confrontiamo il flusso

Da una sequenza a due attività concorrenti

Server iterativo

accept A → gestisci A → A termina → accept B → gestisci B

B può essere collegato, ma deve aspettare la fine di A.

Server concorrente

accept A → avvia thread A → accept B → avvia thread B

I thread A e B possono avanzare nello stesso intervallo di tempo.

Esperimento centrale

Due client serviti senza aspettare

Prodotto atteso: una prova osservabile nella quale A e B ricevono risposta mentre entrambe le connessioni rimangono aperte.

Risultato atteso

B non deve più aspettare che A chiuda la connessione.

Il thread principale ha accettato B mentre il thread A continuava a gestire A.

Confronto finale

Che cosa è cambiato rispetto alla 2.1?

Server iterativo e server concorrente
Server iterativoServer concorrente
Un client viene servito alla volta.Più client possono essere serviti.
Il ciclo principale resta occupato con il client.Il client viene affidato a un thread.
Il nuovo accept() arriva dopo la fine del client.Il thread principale torna rapidamente ad accept().
B può aspettare A.B può essere gestito mentre A è ancora connesso.
!

Il Transmission Control Protocol (TCP) non è diventato diverso.

Abbiamo modificato l’organizzazione del programma server: il socket di ascolto resta unico, mentre ogni connessione viene affidata al proprio thread.

✓

Da ricordare

Accettare nel thread principale, comunicare nei thread dei client

  • listen() viene eseguito una sola volta.
  • Il thread principale ripete accept().
  • Ogni accept() riuscita restituisce un nuovo conn.
  • Il nuovo thread riceve quel conn e gestisce il client.
  • Il socket server resta unico e continua ad ascoltare.
